# PYNQ-Z2 500 ms 声学处理验收

## 目标与已有板端记录

目标为每个完成窗口的声学处理不超过500 ms，包含SRP、候选波束、特征、模型和事件判断。保留48128采样窗口、24064采样更新、14路/48 kHz、完整5580方向/91对、原65抽头波束和模型门限。窗口约1.003 s、更新约0.501 s；500 ms不是从鸣笛开始到照片保存的总延迟，也不把采集窗口缩短到500 ms。

用户提供的上板截图记录SRP 401 ms、波束276 ms、特征55 ms、模型9 ms、声学总736 ms。分项合计741 ms，与总数不同，因此验收应依据同一窗口的`processing_seconds`，不能直接相加不同统计口径的分项中位数。以736 ms为基准，至少需减少约32.1%。本机没有板卡，以下电脑结果不能证明板端达到500 ms。

## Conditioning 专项更新（2026-11-01）

最新`band_conditioned.json`继承下述流式算法，只替换Conditioning。新C库直接处理PCM16或原始PCM码值的float64输入，保留除以32768、0.995去直流、增益、65抽头校准FIR、整数延迟和reset；初始化时保存系数和状态指针，逐包不重算系数或重复传递全部数组。系数/模式在实例内固定，改配置需重建。`feed()`返回独立数组，采集/回放显式使用`feed_into()`及预分配输出；输入必须与输出分离，写入历史窗之后才可覆盖。

使用同一已完成录音，14路、每包512采样，10次轮换配对比较上一版StreamConditioning与buffered/native FIR：

| 配置 | 原C中位 | 新中位 | 新P90 | 新最大 | 配对比例中位 |
|---|---:|---:|---:|---:|---:|
| 无时延/增益校准 | 24.1 μs | 13.5 μs | 19.30 μs | 142.3 μs | 0.552 |
| 仅增益 | 22.5 μs | 11.7 μs | 16.91 μs | 162.1 μs | 0.508 |
| 分数延迟＋增益 | 197.7 μs | 68.3 μs | 84.71 μs | 233.5 μs | 0.344 |
| 跨包长延迟压力 | 516.9 μs | 150.3 μs | 185.71 μs | 1407.7 μs | 0.297 |

单位为微秒/包，机器为AMD64，未在ARM复测；比例按逐包配对计算，不是两个中位数相除。长延迟组包含超过512采样的整数补偿，属于实现压力输入；其最大值仍约1.41 ms，没有明显优于原最大值，不能用中位数声称最坏时延保证。`feed_into()`避免输出分配，但参数检查也有开销，部分配置中不比独立`feed()`更快；它的价值还包括固定存储和明确生命周期。不能把旧波束C实现较慢的结论直接套用到512采样校准微包。

412项完整回归通过，覆盖分区改变、重置、负时延/长整数时延、逐通道冲激、PCM正负极值、非连续/非对齐输入、无输出分配路径及采集/回放缓冲不别名。原NumPy、上一版C、新buffered/NumPy FIR及新buffered/C FIR均作同输入对照，实测最大波形误差约1e-15，容差3e-14。两段公开录音构造阵列流分别含未触发和已知鸣笛正例；默认、增益、分数延迟、长延迟、实际配置下比较三种实现，共90次模型窗口计算，分数、方向、候选和事件一致，最大分数差约4e-15。正例来自已探索验证场景的三次重复，不是独立道路测试；任意人工校准也不代表实际阵列标定正确。

最新包要求另构建`python scripts/build_conditioning.py`，库为`libconditioning.so`、ABI=1；保留既有search/stream两库。`benchmark_conditioning.py`报告六种实现/API的中位/P90/最大值、各校准配置、输入和源码/权重/库哈希，并可用`--model model --input array14.wav`比较模型事件。512/48000约10.67 ms为每包输入周期，报告的周期检查仅适用于当前测试机器；还须在板上验收持续采集和CPU竞争。

本轮仅进一步降低采集线程处理开销，不修改下述SRP/波束/特征/模型，不将每包收益直接加到声学`processing_seconds`中。当前仍无板端500 ms达标证明。原`band_stream.json`、先前冻结实验和部署包保留。新实验产物在`prototype/outputs/conditioning_optimization_v1_20261101/`，详见其中两份benchmark JSON和正例构造记录。

## 先前连续窗口实现

新增可选`config/band_stream.json`，旧`band_fast.json`保持原行为供对照：

- SRP每窗93个STFT帧，连续更新复用46帧，只为47个新帧计算Hann折叠FFT和PHAT。缓存按下一窗口的12帧累加分组保存，包括末尾不足12帧的部分组；恢复原组内single/double累加顺序，再按原顺序汇入double总和。single模式缓存375648 bytes，不保存46帧完整互谱。完整网格、频率梳和麦克风对数不变。
- 波束FFT仍为1024点；752采样步长整除24064更新和48128窗口，保留272采样历史。首窗64块，连续窗复用31块，只重算33块；首块重新补零。直接读取PCM分块视图，减少整窗转置、复制和频谱拼接。
- 方向相同时额外复用有效的波束输出段和45个Mel帧；方向变化时重新合成和提取特征，输入频谱缓存仍可使用。窗首FIR边界和受其影响的特征帧重新计算。Mel矩阵和Hann系数仅初始化一次。
- 状态化C去直流/增益处理减少采集线程的逐包开销；校准FIR仍使用原有NumPy卷积，保留跨包历史和延迟。C库无跨实例全局状态，采集与分析使用独立状态数组。
- 复用要求epoch、采样计数、窗口大小及全部重叠PCM一致；丢包、跳窗、倒序或重叠内容改变时，清空复用路径并重算。不会将缺失数据填零冒充连续输入。

新库为`libstream.so`（Windows测试名`streaming.dll`），ABI=1；既有SRP库仍为ABI=2。库缺失、ABI错误或加载失败时明确报错，不静默切换。仅PS软件有改动，没有新PL核或DMA格式；原采集固件接口保持一致。

输入频谱与模型输入均保留原精度；不采用近似平方根、低精度FFT、减少候选或减少麦克风对来获得本轮结果。公开录音构造场景的1008项独立对拍、84个连续混合窗口、single/double累加逐位测试及全项目376项测试通过。主测试360°/可见联合F1仍为0.6667/0.6308，压力组为0.6512/0.6032，抓拍计数不变。复用的公开来源不是新道路盲测，连续混合窗口只检验实现一致性，不增加新的精度结论。

## 本机配对结果与限制

AMD64、NumPy2.5.3、单线程环境；使用同一输入、同一模型和SRP，与此前`band_fast`比较。下表均为稳态每窗中位数，排除采集等待、视觉、日志和启动：

| 输入 | 原快速版总耗时 | 流式版总耗时 | 逐窗配对比例中位 | 流式版P90/最大 |
|---|---:|---:|---:|---:|
| 原2窗口回放，各重复15次 | 16.09 ms | 11.35 ms | 0.705 | 12.06/12.78 ms |
| 12窗口阶跃方向压力回放，各重复5次 | 17.63 ms | 13.68 ms | 0.780 | 16.67/26.26 ms |

第一组SRP约7.54→5.98 ms、波束5.86→3.60 ms、特征2.07→1.27 ms；模型没有更换，其小幅计时波动不作为优化成果。第二组没有任何输出波形缓存命中，仍减少约22%的总耗时；方向持续变化时收益较低，不能只用静止声源成绩验收。阶跃流由同一PCM录音分块重复并循环置换通道生成，包含不自然的方向跳变，只作缓存和延迟压力测试。

额外epoch失效重算约18.37/20.42 ms，高于对应原版15.71/15.76 ms。首窗与回退路径可能比稳态慢；频繁丢包或跳窗会削弱收益。376项测试中的固定时间不作为性能断言。两个协议连续混合窗口仅27/84窗能复用输出波形，输入FFT/PHAT缓存不依赖这些命中。

原回放中512采样包的Conditioning中位约0.074→0.032 ms；这是单独测量的采集线程内处理耗时，不与并行分析耗时相加。SRP互谱缓存约0.36 MiB，波束输入频谱缓存约3.51 MiB，方向滤波计划最多64项、约7.5 MiB；另有PCM重叠尾部、有限方向输出、Mel缓存和临时数组。这些字节计数不是进程RSS上界，需在板上同时测内存与相机负载。

本轮电脑稳态总耗时减少约22%–30%，不将其乘736 ms推算ARM结果，也不宣称500 ms已实现。保留原基线以便在板端明确判断新实现是否值得启用。

## 板端执行

使用新的部署目录，保留已验收的阵列校准、相机内外参、视觉模型、USB和overlay配置；只合并同款模型的`streaming`节及已有快速参数，不用示例覆盖真实标定。先准备同步14路PCM16/48 kHz的较长录音，建议至少60秒并包含方向变化、背景、静音、强干扰和正常采集负载。

```text
python scripts/build_search.py
python scripts/build_stream.py
python run.py --check
python scripts/benchmark_stream.py --input synchronized-array14.wav --output NEW_STREAM_BENCHMARK.json --windows 32 --repeats 5
python run.py --replay synchronized-array14.wav --output NEW_REPLAY_OUTPUT
python run.py --output NEW_LIVE_OUTPUT
```

仍需同次构建且已验收的采集bit/hwh。两个库都在ARM目标镜像编译，工具不下载依赖、不安装编译器或修改安全软件。Windows DLL不能复制到ARM。运行入口在导入NumPy前为BLAS/OMP设置默认单线程，保留调用者显式环境值；`--check`报告实际环境设置。Python3.6语法检查不替代真实镜像兼容性验收。

`benchmark_stream.py`分别记录初始化、首窗、每次重置、稳态、epoch回退、阶段耗时、计数和源码/输入/权重哈希；固定SRP、模型、门限，仅切换流式复用。另分别测固定和持续变化的候选方向，检查波形、特征及事件。报告中的`all_steady_windows_within_target`只适用于该报告的机器，不得将AMD64的true当作PYNQ验收。

实况事件新增：

- `srp_diagnostics`：`fft_seconds`、`phat_seconds`、`ifft_seconds`、原`search_seconds`及新/复用帧数；融合累加包含在PHAT计时内。
- `beamforming_diagnostics`：新/复用FFT块数、输入FFT与合成耗时、输出复用标记、缓存字节数。
- `stream_diagnostics`：连续性判定、失效原因及每个方向的特征帧复用数。
- `conditioning`：采集线程自上次发出分析窗以来的处理耗时和包数，包含与当前分析并行的工作。

## 验收标准与未完成项

1. 保存实际配置、Python/NumPy/BLAS版本、CPU频率/温度、模型标签405187002及权重哈希。不要在原/新方案之间修改窗口、门限、视觉或功耗设置。
2. 同PCM比较原/新事件、全部候选及分数，原完整网格响应和方向必须在容差内一致；保留静音、弱第二声源、方向变化、缺包/跳窗及饱和结果。先核对数值，再判断速度。
3. 对实际PYNQ报告稳态中位、P90、最大、超过500 ms的窗口数量和比例，首窗/回退单列；deadline目标应看逐窗值，不能只看平均值。长时间开启实际视觉和采集，另查gap、skipped_windows、相机历史覆盖和确认重置。
4. 若不足500 ms，根据新分项证据决定下一步：FFT/PHAT主导时评估ARM FFT实现或PL预处理；空间打分主导时再评估已有层级搜索和全搜回退；波束主导时检查方向变化比例、内存与FFT耗时。不根据电脑计时直接减少方向或麦克风对。
5. 本轮没有新增PL加速。现有可选SRP核仅做插值累加，每窗还涉及约6.09 MB输入、0.089 MB输出以及编码/DMA成本；纯采集overlay没有该DMA。要调整PS/PL分工，仍需合作者完成匹配工程、资源/时序和真实传输测速，不能只比较裸核时间。
6. 已有`WindowBuffer`的削顶标记在样本移出后仍可能保留到历史重置；这是本轮之前的保守行为，尚未改为逐样本窗口标记。本轮未放宽可靠性门限，发生该问题时保留原始包和epoch记录另行修复，不据此提高检测计数。

源码实验入口为`prototype/optimize_stream.py`的`plan`、三个`phase --split validation/test/stress`、`verify`；输入、C库及源码哈希冻结于`prototype/outputs/stream_optimization_v2_20261101/plan.json`。这些产物和本地模型不进入Git。完整部署包、实机剩余工作见[交接文档](HANDOFF.md)。
